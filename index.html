What was actually wrong

Serum splits an order’s life across three places: the order book (bids/asks), your OpenOrders account, and the event queue. When an order leaves the book — filled, cancelled, or evicted — the book writes an out event into the queue, and your OpenOrders slot is only released when that event is consumed (cranked). On this market the cranking stopped years ago, so the paperwork piled up:

  • The 9 sell orders were removed from the book long ago (the asks account today holds only 2 live orders, from other traders; none of the 9 order IDs are in either side of the book).
  • Their 9 out-events were never consumed, so both OpenOrders accounts still count 9 slots as open.
  • Every cleanup path trusts a different half of the system, so each one fails: cancel looks in the book and finds nothing; close counts the slots and refuses; Compass tries to close without cranking this queue and hits the same wall (and would keep 10% for the attempt).
  • Nothing was ever wrong with the funds: both accounts hold exactly 0 token and 0 USDC balances, and the events carry the release-funds flag off with 0 still locked — consuming them is pure slot bookkeeping. No tokens move; only the rent comes home.

Two quirks worth knowing: the queue is first-in-first-out, so the other trader’s 2 events at the head must be consumed in the same pass (permissionless — anyone may crank). And the Serum program looks the accounts up by binary search, so the OpenOrders accounts inside the ConsumeEvents instruction must be passed in the program’s internal sorted order — get that order wrong and the instruction silently consumes nothing.
